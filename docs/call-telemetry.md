# Call telemetry

Client implementation for [iOS issue 411](https://github.com/p-num/element-x-ios/issues/411). The four native event names and properties are preserved: `CallJoinAttempted`, `CallJoinOutcome`, `CallFailure`, `CallParticipationEnded`. Web reports `callPlatform=web`, `callImplementation=embedded`, a random per-join UUID, `dm|group` from the account's `m.direct` mapping, and this component's `VITE_APP_VERSION`. Host observations use their own attempt/source sequence and must not be counted as another successful call.

`CallLifecycle` and `CallCorrelation` supplement those events under schema version 1. Initiation is emitted immediately before `slot.join`; ringing requires a successfully sent positive-lifetime ring notification; connection/reconnection uses `RTCParticipation.state$`'s combined membership and local media connection. The first connected outcome additionally waits for `initialMicrophonePublication$` to confirm any microphone requested at join. Initial mute has no microphone requirement; optional camera failure does not fail an available microphone. This publication evidence stays settled across later mute and reconnection. `connectionScope=localMedia` does not establish remote pickup, microphone audibility or two-way media. Duplicate transitions and all transitions after termination are ignored. A startup failure ends with one failed outcome and one termination; only a once-connected attempt produces `CallParticipationEnded`. Durations use the monotonic clock and `participantsMax` includes self. Embedded host version/build are explicitly `unknown` in component records; the host's own source supplies its authoritative version/build.

The source adapter handles typed SDK errors, not server text. A peer-connection timeout is a typed startup timeout; unanswered ringing is an ordinary remote end, not a Sentry failure. The pickup timer starts after a positive-lifetime ring notification is sent and an eligible recipient is available. The current flow has no bounded timeout for a missing notification or recipient. The current SDK has no general homeserver-join watchdog or terminal slot-close signal in `RTCParticipation.state$`; telemetry does not fabricate either or change call behavior. A reconnect records a disconnection and, on media recovery, a reconnection. A required initial microphone publication rejection produces `microphoneFailed`, a failed join outcome and a handled diagnostic. A browser `NotAllowedError` retained as the SDK error's cause instead records permission refusal without a handled error. Publication failure remains nonfatal to the SDK's receiving connection. The observer reads shared behaviors without consuming events or driving publication.

`io.letro.call_telemetry` carries only `schemaVersion=1`, an increasing widget-wide sequence starting at one, a closed `phase`, optional closed `reason`, and `componentAttemptId`. The existing `WidgetApi` transport supplies the exact widget ID and `api=fromWidget` envelope and owns request/ack addressing. This sender neither manually posts messages nor accepts arbitrary telemetry payloads. A host becomes the sole supplementary component-lifecycle and `attemptLink` owner only when `hostCallTelemetryEnabled=true` and the bridge provides `notifyCallTelemetry`; the Web recorder then suppresses direct `CallLifecycle` records. The flag defaults false, so older hosts retain direct component records without receiving unsupported custom actions. It is independent of reporting consent. A capable host's acknowledgement is validated for `hostAttemptId`, then that host UUID is used for direct participation-correlation records. Its four native-compatible event IDs remain the component UUID. Once host ownership is negotiated, a rejected/missing/invalid acknowledgement leaves Web participation correlation unbound and never starts a second direct lifecycle stream. Without negotiated capability, the component owns direct lifecycle and correlation. Host mirroring and direct Web correlation retain separate platform/source counters; outcome queries select the four component events once. Existing connection-state and new lifecycle messages also have independent widget counters.

## Correlation and privacy

`ParticipationGraph` accepts only full lowercase SHA-256 digests and positive same-snapshot co-membership evidence including the local participation. Its decreasing minimum-root aliases converge after ingestion resolves all observed edges. Room identity, empty snapshots and elapsed time never create an edge. The graph is local to one attempt; it retains already-proven overlap as original group members leave, and a new attempt does not inherit an old room's graph.

The hash preimage is six length-prefixed UTF-8 fields, each prefixed by an unsigned 64-bit big-endian byte length: domain `letro-call-participation-v1`, exact room ID, normalized slot (only the exact aliases `""`, `ROOM`, `m.call#` and `m.call#ROOM` map to `m.call#room`), exact sender, exact member ID, verified generation. Literal `room` remains distinct. With the contract's room/sender/member fixture, literal `room` hashes to `80c431cf2ce574fbbaf2e75330be7ba177af3c409692ef60662b358f449c890b` for `legacy:1234567890` and `56c28d9cd9eb30866df9774de45609794047cb5876425af412ff26554e2650b7` for `per-join`. A verified modern sticky `member.id` uses `per-join`; legacy state membership requires its explicit unsigned `created_ts` as `legacy:<decimal>`. The pinned JS SDK exposes `createdTs()` with a fallback to the refreshed event's timestamp, not a safe legacy generation getter. The adapter uses the public membership parser on the actual matching event obtained from the room timeline, active sticky-event store or legacy room state; it never uses that fallback. If the source event, dialect or generation cannot be verified it stays unbound. No new signaling field or Matrix state is written.

Usage events and edges follow existing PostHog consent. A host-supplied identity is accepted synchronously; standalone first-use boundaries queue while account identification is pending. Events never capture under PostHog's transient pre-identification ID. After identity acceptance, boundaries capture synchronously before teardown. Logout, reset and usage opt-out synchronously clear the pending queue and invalidate its identification revision and generation, so delayed resolution cannot emit a stale boundary. Missing or failed identification drops queued events. The outbound filter removes all automatic URL/referrer/device/person properties from the six event types and drops the historical raw `callId` property from existing analytics events too. Raw room/user/member IDs are used only locally to calculate digests, never sent as properties. Hashes are pseudonymous event context, not anonymous data or immutable universal session IDs.

Each accepted attempt first initializes the normal analytics-choice listener, then captures the centralized analytics generation. Usage opt-out, identity reset and logout invalidate all callbacks from older attempts, including widget reports and handled-error callbacks. Opting back in does not reactivate those attempts. A new attempt accepted while usage analytics is off still has a current lifetime and can report typed failures under independent crash consent. Deferred SDK delivery checks that same lifetime again at the transport boundary.

The embedded host passes exact URL choices `usageAnalyticsEnabled`, `sentryCrashReportingEnabled` and `sentryPerformanceReportingEnabled`; only literal `true` enables each channel, with all three absent flags defaulting off. It supplies `posthogApiHost`, `posthogApiKey`, consented `posthogUserId`, `sentryDsn` and `sentryEnvironment` as routing/identity configuration, independently of those choices. Mobile hosts supply a fresh random UUID for each usage-enabled widget that has a PostHog destination. The embedded package keeps this ID in memory, disables PostHog person profiles, and discards the ID on usage opt-out. Usage reporting resumes in a fresh widget. The scoped PostHog transport accepts only the six call telemetry event types and their declared properties. It rechecks the capture generation on each request, including SDK retries. The full package keeps its existing analytics setting in standalone and widget modes. After content-loaded the host uses `window.controls.setUsageAnalyticsEnabled(enabled)` and `window.controls.setSentryReportingEnabled(errors, performance)` for live changes. There is no reporting-settings widget action. Usage changes update the existing setting for this runtime without persisting over the full standalone user's saved choice. The host passes crash reporting false in Debug; the dedicated reporter additionally rejects non-production/development builds.

Sentry uses the existing error-consent switch from `af2327aad576029d72d3b1cf1774a6f99c7a2dd8`, separately from usage consent, and production builds only. Embedded crash reporting defaults off and can be dynamically revoked by the host. A separate BrowserClient with no integrations constructs handled warning events for typed unsuccessful calls. Scope isolation and `beforeSend` alone are insufficient in pinned JS SDK 8.55.2: global/isolation attachments enter event envelopes, and an internal exception after a throwing processor bypasses `beforeSend`. The dedicated transport therefore authorizes at most 32 locally created event IDs for 120 seconds, retaining immutable typed payloads. Before calling the existing fetch transport, it validates the event identity/type, consumes its authorization once, rechecks live crash consent and the attempt lifetime, and reconstructs the whole envelope from the trusted payload. No SDK envelope headers, dynamic sampling/baggage/trace, attachments, sessions, client reports, users, requests, breadcrumbs, SDK logs, extras or arbitrary contexts survive. Internal recovery IDs and all unrecognized/nonconforming envelopes fail closed. Cause/phase deduplication retains at most 32 attempt UUIDs. Reporting fails closed on a different SDK version until its wire-envelope tests are reviewed. The ordinary embedded Sentry transport retains crash types, source-map metadata, trace timing, closed span operations and status codes, and standard numeric browser measurements. It drops widget URLs, dynamic transaction names, request data, free-form messages, breadcrumbs, attachments and arbitrary contexts before serialization. Embedded Sentry does not attach tracing headers to application requests. Its default environment is `production` when the host supplies no value. Grouping uses only `call-failure/cause/phase`; UUIDs never participate in fingerprints. Permission refusal, decline, abandonment and local hangup do not generate handled errors. Delivery remains best effort. Existing release/source-map/scrubber work (`0b964f71`, `0c3eeea7`) remains a separate operational dependency; this change does not ship that active worktree or claim deployed source maps.

## DevOps handoff: decide before deployment

No ingestion service, Grafana dashboard, DNS/TLS/ingress change or cluster dependency is deployed by this client work.

The existing client sends usage analytics through the configured PostHog project and handled diagnostics through its configured Sentry DSN. The workspace also has existing Grafana/Loki/Tempo/Prometheus infrastructure; its live routing and tenancy must be verified by its owner before choosing an integration. Start by reusing that stack and existing authenticated ingestion/routing, rather than adding a second collector solely for these clients.

| Decision                   | Smallest reuse-first option                                                                                                              | Alternatives and tradeoffs                                                                                                                                                                                                 |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Authentication and routing | Existing authenticated telemetry gateway, preserving usage and error-consent channels                                                    | A dedicated gateway offers isolation but adds service ownership, credentials, deploys and on-call work. A public client key alone is not user authentication.                                                              |
| Storage and queries        | Existing Loki event storage and Grafana queries; existing Tempo only where an approved trace pipeline already exists                     | PostHog export into existing storage may reduce client changes but needs export credentials, replay/deduplication and lag monitoring. Do not turn every event into a trace.                                                |
| Retention and access       | Reuse an approved tenant, role policy and expiry policy for pseudonymous event context                                                   | A separate tenant gives stronger separation but adds retention, access and deletion workflows. Decide whether alias lifetime must cover the entire retained event window.                                                  |
| Abuse and cardinality      | Existing rate limits, payload size limits and schema validation at ingress                                                               | Per-client/per-user controls require a reviewed authenticated identity; device/attempt/session hashes must not become Prometheus labels. Closed cause/platform/version/kind metrics can be aggregated server-side.         |
| Sampling                   | Explicitly decide whether complete outcome counts or sampled diagnostics are needed                                                      | Independent edge sampling can split sessions. If sampling is necessary, define consistent inclusion and incomplete-correlation reporting before treating aggregates as complete.                                           |
| Alias resolution           | Resolve decreasing aliases transitively in the ingestion/query path before session aggregation                                           | Query-time resolution avoids a new service but may be expensive; a durable resolver speeds queries but needs ordering, idempotency, state, expiry, backfill and failure ownership. Never merge missing edges by room/time. |
| Deduplication              | `(platform, component attempt UUID, source, sequence)` for supplementary records; native attempt/event semantics for four outcome events | Host/component `attemptLink` relates two sources without counting two calls. Widget close alone must not guess local/remote attribution.                                                                                   |
| Alerting and rollout       | Existing Grafana alert routing after retained-event/query validation                                                                     | Agree alert thresholds, minimum sample size, release cohort, suppression and responder ownership; client unit tests do not prove alerts or released ingestion.                                                             |

Before approving any new topology, DevOps should record the current gateway/tenant/route, chosen reuse option, operational owner, data retention/access policy, abuse/sampling/cardinality limits and alias-resolution algorithm. A staged validation should demonstrate auth rejection, schema rejection, consent revocation, out-of-order/duplicate edge convergence, repeat calls in the same room remaining separate and cross-platform source deduplication. Only then can a reviewed dashboard and alerts be evaluated against actual released-client traffic.
